# GX10 access

The ASUS Ascent GX10 is the shared hackathon machine. The app, the model, and everyone's development all run on it. Everyone reaches it over Tailscale.

| | |
|---|---|
| Tailscale name | `1s6m` (full: `1s6m.taild3a24b.ts.net`) |
| Tailscale IP | `100.123.175.71` |
| User | `asus` |
| Password | `password` |

Machine details (OS, desktop session, models, and what's installed) are in [planning/grounding.md](planning/grounding.md). Setup steps (packages, tray extension, Python, music, model) are in [setup.md](setup.md).

## Getting on

1. Install Tailscale on your laptop and join the team's tailnet (`taild3a24b`). Ask whoever owns the tailnet to invite you or share the `1s6m` node with you.
2. Check that it's reachable: `tailscale status` should list `1s6m`.
3. Connect:

   ```sh
   ssh asus@1s6m        # or ssh asus@100.123.175.71
   ```

   Optional: `ssh-copy-id asus@1s6m` so you don't have to type the password each time.

4. Editors: VS Code or Cursor Remote-SSH to `asus@1s6m` works the same way.

Tailscale works from any network (venue Wi‑Fi, eduroam, hotspot, or off-site), so the same commands work after the venue closes.

## Running agents on the GX10

- Run your coding agent on the GX10 inside `tmux`, so it keeps working if your SSH connection drops: `tmux new -s <your-name>`, and later `tmux attach -t <your-name>`.
- Each agent works in its own worktree next to the main checkout (see [CONTRIBUTING.md](../CONTRIBUTING.md)).
- `gh` is not installed on the GX10 yet ([setup.md](setup.md) step 1). Everyone shares the `asus` account, so each person sets their own `GH_TOKEN` in their tmux session ([setup.md](setup.md) step 3).

## The screen and the desktop session

- There is one real screen. The desktop session is **X11** on display `:1`.
- Anything that captures the screen, controls windows, or shows an overlay has to target that session, even when started from SSH:

  ```sh
  export DISPLAY=:1 XAUTHORITY=/run/user/1000/gdm/Xauthority
  ```

- If the screen is locked or the monitor is asleep, screenshots come back black. Someone has to unlock it at the machine for real capture tests.
- Only one person at a time should run the full capture loop against the real screen.
- Keep logging in to the Xorg session. Switching to Wayland would break screen capture and window control from external tools.

## Models

- **Qwen3.8 Flash Next is live** on vLLM 0.31: model `qwen3.8-flash-next`, local endpoint `http://127.0.0.1:18300/v1`, remote Tailscale endpoint `http://100.123.175.71:18300/v1`. The bearer key stays in `~/.config/qwen38/api-key`; never print or commit it.
- **Ollama is deliberately stopped. Do not start it or another large model beside vLLM**, which uses about 97 GiB of the shared machine's memory.
- Check status with `cd ~/gx10-model-plan && ./gx10.sh status`. Serving operations are in `~/gx10-model-plan/RUNBOOK.md`.
- Fresh Daybook configs use Qwen3.8 with configurable concurrency two. Existing config files are preserved; follow [setup §6](setup.md#6-the-model) to select and verify the profile for the intended `DAYBOOK_HOME`. The older grounding measurements are historical, not an instruction to load Ollama.
